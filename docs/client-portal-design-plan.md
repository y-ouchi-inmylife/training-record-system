## 1. 方向性

飼い主が週に一度、犬を預けている場所から「今日はこんなことをして、こう変わってきましたよ」という便りを受け取る場所にする。 業務ツールでも管理画面でもなく、**トレーナーからの手紙が時系列に届く受箱**として設計する。写真や動画は独立したギャラリーではなく、その日の便りの中に添えられているという構造にする。

## 2. カラー

Bootstrap 既定の `#fd7e14`（.bg-client-nav）は破棄する。あのオレンジはビジネスチャットの通知色に近く、犬と飼い主の関係性を表す色ではない。以下 6 色を新設する。

コントラスト比は実測（WCAG 2.2 の 1.4.3 テキスト = AA 4.5:1 / AAA 7:1、1.4.11 非テキスト = 3:1 が基準）。

| トークン | HEX | 用途 | 主要組み合わせの実測コントラスト | なぜこの色か |
|---|---|---|---|---|
| `meadow` | `#EEF1E8` | ページ背景 | forest on meadow = **13.04:1** ✓AAA | 既定になりがちな「クリーム（#F4F1EA）」を意図的に外し、緑寄りの中間色を選ぶ。屋外・草の匂いを暗示するが、装飾ではなく背景として引く |
| `chalk` | `#FBFAF6` | カード・入力欄の面 | forest on chalk = **14.27:1** ✓AAA | `meadow` からわずかに浮くほぼ白。純白（#FFFFFF）にすると背景と分離しすぎ、カードが硬く見える |
| `forest` | `#1E2A22` | 本文・見出しのインク・フォーカスリング | 全ての明色上で 8:1 以上 | 黒ではなく緑を帯びた深い色。テキストの主色。65% で副次テキスト、45% でメタ情報として不透明度で階層をつける。**フォーカスリングの主色も兼ねる**（A-1 で用途拡張） |
| `biscuit` | `#E8B57A` | 主要 CTA・タグ背景・「日付ブロック」の帯 | forest on biscuit = **8.03:1** ✓AAA | 犬用ビスケットの温かい黄土色。`forest` の文字とペアで AAA を確保。テラコッタ（AI 既定の第3の色）を避けたかったので、より黄味に寄せた |
| `tennis` | `#C9D64B` | **面としてのみ使用**（成功トースト等の背景、`forest` テキストを載せる） | forest on tennis = **9.37:1** ✓AAA<br>tennis on chalk = **1.52:1** ✗<br>tennis on meadow = **1.39:1** ✗ | テニスボールの黄緑。飼い主が犬との遊びで既に肯定的な意味を刷り込まれている色。**明色上で 3:1 に届かないため、線・小さな図形・状態インジケータには使えない**。面として塗り、その上に forest 文字を載せる用法に限定（詳細は §2-1）。今回の**アクセントの賭け**（詳細は §7） |
| `siren` | `#B45438` | エラー・破棄アクション・無効リンク（**chalk 面上に限る**） | siren on chalk = **4.71:1** ✓AA<br>siren on meadow = **4.31:1** ✗ | 温かみのある煉瓦色。`biscuit` の黄色成分を落として赤に寄せた。Bootstrap の危険色 `#dc3545` は青みが強くパレット全体から浮くため使わない。**meadow のページ背景上には配置しない**（詳細は §2-1） |

Bootstrap 既定の緑は導入しない。成功系メッセージは `tennis` 面 + forest 文字で表現する（境界の可視化は §2-1 参照）。

### 2-1. 色の使用制約（アクセシビリティ由来）

実測結果から、以下の 3 点を設計上の**禁止事項**として明文化する。実装時に迷わないための約束。

#### tennis の禁止用途
- **フォーカスリングに tennis は使わない**（1.4.11 未達）。代替: `forest` 2px アウトライン + 2px `chalk` オフセットの二重輪郭。明色上で 13:1 以上、`biscuit` 面上でも 8:1 を確保する
- **「新着」等の状態インジケータに tennis は使わない**（1.5:1 では情報が伝わらない）。将来インジケータが必要になった場合は `forest` 等の濃色を使う
- **細線・アイコン・小さな図形に tennis は使わない**。面（塗り）としてのみ使用

#### siren の配置制約
- **siren のテキスト・アイコンは `chalk` 面上（カード内・入力欄内・入力欄直下の invalid-feedback）にのみ配置する**
- ページ背景（meadow）に直接エラー文言を置く設計にしない
- ページ全体に対するエラーが必要な場合は、まず `chalk` のバナー（カード）で包み、その中に siren テキストを載せる

#### tennis 面（成功トースト等）の境界
- tennis 面は背景 meadow に対して 1.39:1 のため、輪郭が消える。以下を必ず組む：
  - **1px `forest` の外枠**（forest on meadow = 13.04:1 で境界自体は確実に可視）
  - **軽い落ち影** `box-shadow: 0 4px 12px rgba(30, 42, 34, 0.15)`
  - 内部テキストは `forest`（tennis 面上で 9.37:1）
- これにより WCAG 1.4.11（UI コンポーネントの境界 3:1）を、塗りではなく**外枠**で満たす

## 3. タイポグラフィ

日本語主体・スマートフォン主体・毎日は開かない読者。この 3 条件から、**Web フォントは 1 種類だけ、ディスプレイ用に薄く効かせる**方針にする。

### 書体の役割

| 役割 | 書体 | 採用可否 | 理由 |
|---|---|---|---|
| ディスプレイ（H1 / 日付ヘッドライン） | **Zen Old Mincho** Regular 400 | 採用 | Google Fonts に日本語 subset があり、`unicode-range` による動的サブセットで実効 30〜80KB。人肌のある明朝体で「便り」というメタファーを支える。使う場所を絞る（各ページ 1〜3 箇所）ので `font-display: swap` の再フローも許容範囲 |
| 本文・UI テキスト | システム日本語スタック `-apple-system, BlinkMacSystemFont, "Hiragino Kaku Gothic ProN", "Yu Gothic", "Meiryo", sans-serif` | 採用 | ダウンロードコストゼロ。飼い主が普段からスマホで見慣れているレンダリングと同じで、ここで攻める意味がない |
| 本文の代替として Noto Sans JP | Noto Sans JP | **不採用** | 一貫性は上がるが、モバイル読者に対して +150KB 以上（Regular + Medium で）の追加コスト。この画面群は本文で個性を主張する必要がない |
| 数字・データ用 mono | JetBrains Mono / Space Mono など | **不採用** | 日付や件数の桁揃えは本文書体の `font-variant-numeric: tabular-nums` で解決する。mono を投入するのは AI が反射で選ぶ「テック風の格好つけ」で、このブリーフに合わない |

### 型スケール

Bootstrap の rem を維持する。行間は日本語のため 1.5〜1.8 に持ち上げる（Latin 想定の Bootstrap 既定 1.5 は日本語で詰まって見える）。

| 役割 | サイズ | 書体 | ウェイト | 行間 | 用途例 |
|---|---|---|---|---|---|
| Display | 2.5rem | Zen Old Mincho | 400 | 1.3 | ログイン画面のワードマーク、詳細画面の日付見出し |
| H1 | 1.75rem | Zen Old Mincho | 400 | 1.4 | ダッシュボードの挨拶 |
| H2 | 1.375rem | Zen Old Mincho | 400 | 1.4 | セクション見出し（使用は最小限） |
| H3 / カード内見出し | 1.125rem | システム sans | 600 | 1.5 | セッションカード内のトレーニング種別など |
| Body | 1rem | システム sans | 400 | 1.75 | 本文・ノート |
| Meta | 0.875rem | システム sans | 400 | 1.6 | 時刻・件数・キャプション（`forest` 65%） |
| Micro / Eyebrow | 0.75rem | システム sans | 500 | 1.4 | 「今週のトレーニング」等の小見出し（`forest` 65%、字間を軽く広げる `letter-spacing: 0.08em`） |

### 数字の扱い

日付・件数・電話番号など、桁揃えが読みやすさに直結するものは `font-variant-numeric: tabular-nums` を効かせる。日付ブロック（§4 参照）の大きな数字だけ Zen Old Mincho で組み、他は本文書体で揃える。

## 5. シグネチャー

**日付ブロック**。セッションカードの左端に `biscuit` 色の帯を置き、そこに **月（`8月`）・日（`2`）・曜日（`金`）を日本語のまま縦組みで大きく**配置する。日は Zen Old Mincho で 2〜3rem。カードの本体には写真とノートが並ぶ。

**日本語表記を選ぶ理由**：
- 読者は日本語主体・IT に詳しいとは限らない飼い主。英語の月名・曜日略号を最重要要素に置く根拠がない
- `AUG / 2 / FRI` は欧米のカレンダーチップ UI からの借用で、海外 SaaS に広く存在する形。「一目で他と区別する要素」というこの節の主張と矛盾する
- 縦組みの日本語数字は Zen Old Mincho を選んだ理由（人肌のある明朝、日本語の便り）と整合し、むしろ独自性が出る

このブロックが**このポータルを一目で他と区別する要素**。以下を同時に解く：

- 「この写真はいつのものか」がカードの一部として常に語られる（問題 2 の解決）
- フィード全体を上から下にスクロールしたときに、日付が視覚のリズムを作る（週の流れが体感できる）
- 過去に遡るほど自然に「時間の重なり」が可視化される（毎週 1 枚積もっていく感覚）
- 犬の名前・写真を将来受け取る余地を、日付ブロックの**下段**に確保できる（現状は非表示、将来「タロウ」等が入る）

装飾（封筒・ハンコ・破線）は一切入れない。純粋な色帯と縦組みの日本語だけでシグネチャーを成立させる。

## 7. 自己批評

**どこが凡庸か、何を変えたか**を正直に書く。

1. **「暖色ニュートラル背景 + 暖色アクセント」は AI が犬・温かさ・親しみのブリーフで反射的に出す第 1 の答え**。私も一度、`meadow` の代わりに `#F4F1EA`（クリーム）を検討した。これは skill が名指しした AI 既定パターンそのもの。→ 背景の色相を緑寄り（#EEF1E8）に振り、アクセントに **tennis-ball 黄緑（#C9D64B）** を組み込んで既定パターンからの離脱を明示した。

2. **明朝ディスプレイ + システムサンス本文の組み合わせも典型 AI 選択**。ただし今回は日本語主体・モバイル主体・情緒的な読み物という 3 条件が全部揃っており、この選択は**ブリーフに正当化される**。既定だから避けるのではなく、既定を選ぶ理由を明示することで対処した（§3）。

3. **カード型フィード**という構造も定番。特別なのは **日付ブロックのシグネチャー（§5）**と、**カード内スクロールを絶対に作らないという規律**の 2 点。フィード形式を選ぶこと自体はありふれていることを認める。

4. **「便り／手紙」というメタファー**は執行を誤ると幼稚になる。私も初期案では封筒アイコン・切手モチーフ・ワックスシールボタンを検討したが、全て却下した。メタファーは**構造（カードが便りに、日付ブロックが消印に相当する）だけで語り、装飾では語らない**。

5. **ダッシュボード先頭を「最新のトレーニング」1 枚**にしたのは、いわゆる「hero + feed」のよくあるパターンだが、テンプレート的な「大きな数字＋小さなラベル＋補助グラフ」を組まない点で AI 既定と分岐している。hero = 単に **最新のセッションカードそのもの**を大きくしただけで、装飾的な指標カードは作らない。

6. **番号付きの process markers（01/02/03）**は skill が警告する定番。intake の 3 点シェブロンは 1/2/完了という**実際の順序を持つ工程**なので採用可、と判断した。ダッシュボードの記録フィードには番号付きマーカーを付けない（時系列であって順位ではない）。

7. **見落としだった：日付ブロックを `AUG / 2 / FRI` の英語表記で組んだのは、AI 既定の欧米カレンダーチップ UI（Google Calendar / Notion カード / 多くの海外 SaaS）からの反射的な借用だった**。読者が日本語主体・IT に詳しいとは限らない飼い主であることを与えられていたのに、シグネチャーの主役に英語を置いた。「一目で他と区別する要素」を語りながら、同時に「海外にも似た形が広く存在する要素」を採用しているのは矛盾。→ `8月 / 2 / 金` の日本語縦組みに変更した（§5）。Zen Old Mincho を選んだ理由（人肌のある明朝、日本語の便り）とも整合し、独自性が上がった。

8. **アクセシビリティを実測で検証していなかった**。初版では `tennis` をフォーカスリング・新着ピップに割り当てていたが、tennis on chalk = 1.52:1 / tennis on meadow = 1.39:1 で WCAG 1.4.11（非テキスト UI 3:1）を大きく下回っていた。実測してもらって初めて発覚した。→ tennis は面（+ forest テキスト）専用に限定、フォーカスリングは `forest` 二重輪郭、新着表示は `forest` 塗りの小丸へ差し替え（§2-1）。「読み物として気持ちがよい」ことと「情報伝達が成立している」ことは別の要件で、後者は測ってから決める。

9. **候補外だった選択肢**：
   - Bootstrap 既定 `#fd7e14` の維持。ビジネス通知色で、飼い主の感情に合わない
   - Noto Sans JP を全域投入。モバイル読者への +150KB を正当化できない

#### 8-1-1. DashboardController の変更内容

**既存クエリはそのまま使える。変更するのは取得後にビューへ渡すデータ構造だけ**。

現状の `index()` は以下のクエリで既にセッションカード・フィードに必要な情報を全て取得している：

```php
auth('client')->user()
    ->trainingRecords()
    ->with(['trainer1', 'trainer2', 'trainingType', 'mediaRecords'])
    ->withCount('mediaRecords')
    ->orderByDesc('training_date')
    ->get();
```

- **eager load のセット**（trainer1, trainer2, trainingType, mediaRecords）は既に存在する。N+1 は発生していない
- **`training_date` 降順ソート**も既に存在する
- **`withCount('mediaRecords')` は現状のまま残す**。`mediaRecords` が eager load 済みのため `$record->mediaRecords->count()` でも件数は取れるが、今回の目的はデザイン改良でありコントローラの整理ではない。差分を増やさない
- **クエリの起点は `TrainingRecord::` の静的呼び出しではなく `Client` の HasMany 経由**（`Client.php:142-145` に `trainingRecords(): HasMany` が定義されている）

##### 変更 1: `$mediaItems` を「平坦化」から「記録ごとの入れ子」へ組み替える

現状の `$mediaItems` は「記録×メディア」の**平坦配列**として組み立てられており、記録との紐付けが失われている。カード内スクロール廃止・記録単位表示のために、これを**記録ごとに入れ子の構造**に組み替える。

**「廃止する」のではなく、構造を変える**。理由：現状の `$mediaItems` 構築ループの過程で、各メディアについて以下の値がコントローラ側で生成されている。これらは Blade からモデルを辿るだけでは取得できないか、または Blade で呼ぶべきでない：

- `thumbnailUrl`: `$m->temporaryThumbnailUrl($thumbnailExpiresAt)` — **署名付き URL**。有効期限を渡して都度生成する必要があり、Blade ではなくコントローラで一括生成する
- `conversionStatus`: 「準備中です」表示（§6 文言書き換え表）の判定に必要
- `displayTitle`: `title` が空のとき `original_filename` にフォールバックするアクセサ値
- `type`: `photo` / `video` の分岐

これらは**引き続きコントローラで生成する**。有効期限の算出（現状の `$thumbnailExpiresAt`）もそのまま維持する。

概念的な返却構造（変数名・型は実装時に調整可）：

```
$sessions = [
  [
    'record' => $rec,          // TrainingRecord モデル（そのまま渡す）
    'media'  => [               // その記録のメディア配列（平坦化はしない）
      ['id' => ..., 'type' => ..., 'thumbnailUrl' => ...,
       'conversionStatus' => ..., 'displayTitle' => ...],
      ...
    ],
  ],
  ...
];
```

hero と feed への分割は、この `$sessions` を Blade 側で `first()` / `skip(1)` するか、コントローラで `$hero` / `$feed` として先に分けてから渡すか、いずれでもよい。実装時に判断する。

##### 変更 2: ノート表示に使うフィールドは `record_content` に確定する

`TrainingRecord` には `record_content` と `impression` の 2 つのテキストフィールドがある（`$fillable` で確認）。**セッションカードのノート冒頭（§4-2）と詳細画面のノート本体（§4-4）に使うのは `record_content` のみ**。

根拠：

1. **クライアント側 `client/training-records/show.blade.php` は現在 `record_content` を表示している**（line 76-77 該当行引用）：
   ```blade
   @if($trainingRecord->record_content)
       <div>{!! nl2br(e($trainingRecord->record_content)) !!}</div>
   ```
2. **`impression` はクライアント側のいずれの画面にも表示されていない**（`resources/views/client/` 配下を grep 済、0 件）。トレーナー側の登録・編集フォーム（`training-records/_form.blade.php`）と、トレーナー側詳細（`training-records/show.blade.php` の `section-impression` 折りたたみ）でのみ表示される
3. **決定的な根拠**: `src/app/Http/Controllers/Client/TrainingRecordController.php:16` のクラスコメントに以下の宣言がある：
   > 所感（impression）・最終更新者などクライアント非開示情報は

つまり `impression` は**設計上クライアント非開示のフィールド**。トレーナーの内部所見であり、飼い主に見せる判断は本プランの範囲外。

**禁止事項（明文化）**：

- セッションカードのノート冒頭・詳細画面のノート本体は **`record_content` のみを使用**する。`impression` を代替として使わない
- **現状クライアント側に表示していないフィールド（`impression`, `updated_by` 等）を、今回の再構成で新たに露出させない**。表示可否の判断は本プランの範囲外であり、必要になれば別プランで扱う

##### メディアが多対多である事実（実装者向けの注意）

`TrainingRecord::mediaRecords()` は **`belongsToMany`** であり、中間テーブル `media_record_training_record` を介する（`withPivot('sort_order')` / `orderByPivot('sort_order')`）。逆方向 `MediaRecord::trainingRecords()` も `belongsToMany`。

DashboardController.php:33 の既存コメントにあるとおり、**同じメディアが複数のトレーニング記録に紐づく場合がある**。フィード形式では**同じ写真が複数のセッションカードに現れ得る**。

これは仕様通りの挙動であり、今回の設計変更で対処すべき問題ではない。ただし実装者が「重複表示のバグ」と誤解して重複排除を入れてしまわないよう、事実として明示しておく。

#### 8-1-2. vite.config.js 変更の副作用と確認手順

- `public/build/manifest.json` は Vite が全エントリを一括管理する**単一ファイル**であり、トレーナー側の `app.blade.php`（`@vite(['resources/sass/app.scss', 'resources/js/app.js'])`）とクライアント側の `client.blade.php` などが**同じ manifest を参照**する
- エントリを追加すると manifest が**再生成される**。Hash 付きファイル名も変わり得る
- `public/build/` は Git 管理対象のため、**ビルド成果物を同一コミットに含める**こと。ビルドし忘れの状態を push すると本番でアセットの 404 が発生する
- 実装後、以下を必ず確認：
  1. `npm run build` を実行
  2. `public/build/manifest.json` の差分に `client.scss` エントリが追加され、既存の `app.scss` / `app.js` エントリのハッシュも同時に更新されていることを目視
  3. **トレーナー側の代表画面を目視確認**（ログイン・ダッシュボード・クライアント一覧・トレーニング記録一覧・トレーニング記録詳細）— スタイル崩れ・404 が出ないこと
  4. **クライアント側の代表画面を目視確認**（ログイン・ダッシュボード・トレーニング記録詳細・intake フォーム）
  5. `public/build/` 配下の生成物と manifest 差分を、Blade / SCSS の変更と**同一コミットに含めて**コミットする
