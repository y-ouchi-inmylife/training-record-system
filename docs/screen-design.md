#### 2-1-2. 表示挙動

トレーナー側のナビゲーションバーは、スクロール時も画面上端に留まる（Bootstrap の `sticky-top`）。一覧・詳細画面は縦に長く、他画面へ移動するために毎回先頭まで戻る操作を省くため。

クライアント側のナビゲーションバーは通常フローのまま（スクロールすると画面外へ流れる）。画面数が少ないため。ナビには**「登録情報」（S-1406 クライアント登録情報画面へ）と「ログアウト」**を配置する（回遊要素は最小限。詳細は `docs/client-portal-design-plan.md` §4-0）。スマートフォンでは折りたたみメニューの中に、「登録情報」と「ログアウト」を並べて置く。

### 2-3. ブラウザタイトル

ブラウザタブに表示される `<title>` は「**画面名 - サフィックス**」形式で統一する。

#### 供給元

| 側 | 対象レイアウト | サフィックス |
|---|---|---|
| トレーナー側 | `layouts/app`・`layouts/guest`・`layouts/error` | `config('app.trainer_portal_name')`（既定値「トレーニング記録管理システム」） |
| クライアント側 | `layouts/client`・`layouts/client-public` | `config('app.client_portal_name')`（既定値「トレーニング記録」。クライアント側プロダクト名の詳細は `docs/client-portal-design-plan.md` §9-1 を参照） |

#### 記述規約

- **画面名は各 Blade の `@section('title', ...)` で機能名のみを渡す**（例: `@section('title', 'クライアント一覧')`）。
- **サフィックスはレイアウト側で `<title>` タグ内に後付けする**。`@section('title', ...)` 側でサフィックスを連結してはならない（連結すると規約から外れた画面ごとに手当てが発生する）。
- `@section('title')` が未指定の画面は、レイアウトの `@hasSection('title')` 分岐によりサフィックスのみを表示する（先頭に「 - 」が付かないこと）。

#### 例外

1. **`recording-v2/session.blade.php`** はレイアウトを継承せず `<title>録音実行</title>` を直書きしている。音声記録機能に属する画面のため、本規約の適用対象外。
2. **ダッシュボード**（トレーナー側 `dashboard.blade.php` / クライアント側 `client/dashboard.blade.php`）は `@section('title', ...)` を渡さず、サフィックスのみを `<title>` に表示する。各ポータルの入口にあたる画面のため、画面名を重ねない。

### 2-4. 未入力値の表示

値が未入力・未設定の項目は、表示形式に応じて次のように扱う。

**セル形式（ラベル上・値下）**

- 何も表示しない（ラベルのみ残す）
- セルは最小高さを持つため、値の有無で行高は変わらない
- 対象: `x-detail-cell` を使う箇所（トレーナー側の 3 列グリッド）、およびお客様側の縦一列表示（S-1406 など。`client-portal-design-plan.md` §2-3 参照）、そのほか同形式で直接記述した箇所

**テーブル形式（`<td>`）**

- 「—」（em dash）を表示する
- 空にすると行高が不安定になるため
- 対象: 一覧画面のテーブル、詳細画面の項目テーブル

**本文・自由記述**

- 行ごと非表示にする
- 対象: トレーニング記録タイムラインの記録本文など

### 2-5. バッジ

バッジ（`.badge`）は、サイズで重要度を、配色で意味を表す。

**サイズ**

| 種別 | 指定 | 用途 |
|------|------|------|
| 強調バッジ | `fs-6` を付ける | 対応の要否を示す状態表示。見落とすと業務に支障が出るもの |
| 標準バッジ | 指定なし（Bootstrap 既定） | 分類・種別のラベル。読めればよく、目立つ必要がないもの |

**配色**

| 配色 | 意味 | 例 |
|------|------|-----|
| `bg-success` | 正常・完了 | 利用中、未使用（有効なURL） |
| `bg-warning text-dark` | 要対応・注意 | 初回設定待ち、メールアドレス登録待ち |
| `bg-secondary` | 未着手・無効 | メールアドレスなし、使用済み |
| `bg-danger` | 異常・期限切れ | 期限切れ |
| `bg-light text-dark border` | 分類ラベル（意味を持たない） | トレーニング内容 |

**クライアント状態バッジの 4 状態対応**（S-0304・S-0305 で使用）

| バッジ文言 | 配色 | 添え書き（該当時） |
|------|------|------|
| 利用中 | `bg-success` | — |
| 初回設定待ち | `bg-warning text-dark` | 有効期限切れなら「（期限切れ）」を添え、配色を `bg-danger` に切り替える |
| 登録待ち | `bg-warning text-dark` | 有効期限切れなら「（期限切れ）」を添え、配色を `bg-danger` に切り替える |
| なし | `bg-secondary` | — |

**太さ**

Bootstrap 既定（`font-weight: 700`）を使い、個別に変更しない。

※ 本規約は新設・改修する画面から順次適用する。既存バッジの棚卸しは別途行う。

※ クライアントポータル（S-1401〜S-1405）の配色は `docs/client-portal-design-plan.md` §2 のトークンに従い、本表の適用外とする。

## 3. 画面詳細

**記載範囲**:
- 本章では、本システムが提供する全画面を列挙する。
- 全画面とは、要件定義書（docs/requirements.md）の7章「画面一覧」で挙げられている画面を指す。
- 各画面のデザイン・インターフェイス・遷移の把握を目的とする。

**参照ルール**:
- 各画面の概要・提供機能・アクセス権限は、要件定義書（docs/requirements.md）の7章「画面一覧」で管理している。本書では同じ画面IDを使用しているため、画面IDで突き合わせて参照すること。

**画面 ID の欠番**:
- **S-0302** — もとから欠番
- **S-0303** — 段階 1 の事前入力 URL 廃止で欠番化（他文書からの参照ずれを防ぐため番号は繰り上げない）
- 画面 ID を新設する場合は既存の欠番を埋めず、末尾に採番する（例：クライアント側は S-1408 が最後、次の空き番号は S-1409）

**記載する項目**: 各画面について、以下の項目を記載する。
- **ワイヤーフレーム**（必須）: 画面の構成要素と配置を示すテキストベースの図。罫線で囲み、ナビゲーションバー・主要な入力欄・ボタン・テーブルなどを記載する。
- **画面項目**（必須）: 画面上で表示・入力する項目の一覧。「項目名」「種類」「必須」「説明」の4列で記載する。テーブル形式の項目は別途列定義表を「列」「種類」「必須」「説明」の4列で記載する。
- **バリデーション**（必須）: 入力チェックとエラーメッセージ。「項目」「チェック内容」「説明」の3列で記載する。チェック不要な場合は「なし」と記載する。
- **状態一覧**（必須）: 画面の表示モードや状態を切り替える場合の各状態の説明。状態の切り替えがない場合は「なし」と記載する。
- **操作フロー**: ワイヤーフレームと画面項目だけでは伝わりにくい画面内の挙動を、ユーザーの操作順に記述する。業務フローは記載しない（業務フローは要件定義書で扱う）。
- **備考**: 業務的・運用的に重要な特記事項がある場合のみ記載。

**必須欄の記号**: 「画面項目」「バリデーション」表の「必須」列では、以下の記号を用いる。

| 記号 | 意味 |
|---|---|
| ● | 必須 |
| ▲ | 条件付き必須（説明欄で条件を「※」付きで明示する） |
| 空欄 | 任意 |

**画面項目の種類**: 各画面の「画面項目」表で使用する「種類」列の値は、以下のいずれかを用いる。

| 種類 | 説明 |
|---|---|
| 表示のみ | 値を表示する（編集不可） |
| テキスト | 1行のテキストを入力する |
| テキストエリア | 複数行のテキストを入力する |
| 数値 | 数値を入力する |
| 日付 | 日付を入力する |
| 時刻 | 時刻を入力する |
| 電話番号 | 電話番号を入力する（数字とハイフン） |
| メールアドレス | メールアドレスを入力する |
| パスワード | パスワードを入力する（入力値はマスク表示） |
| プルダウン | 選択肢から1つを選択する |
| はい／いいえ | フラグのオン／オフを切り替える |
| ファイル選択 | ファイルを選択する |
| ボタン | 操作を実行する |
| リンク | 別画面へ遷移する（テキスト形式） |
| カード | 情報を1単位にまとめて表示する（クリックで遷移する場合あり） |
| テーブル | 複数行のデータを一覧表示する |
| 動的リスト | 行を追加・削除できる入力リスト |
| 画像 | 画像を表示する |

**パスワードの強度**: 
- 8文字以上
- 大文字・小文字・数字・記号をそれぞれ1文字以上含む
- よくあるパスワード（password 等）を禁止

- 2カラム本体は Bootstrap グリッドで左 `col-lg-8`（トレーニング記録）／右 `col-lg-4`（予備カード）に分ける。`lg` 未満では縦積みとする

- 「メールアドレスを削除」ボタンは**利用中のときだけ表示**する（頻度が低く影響が大きい操作のため、確認モーダルを挟む）

##### 状態一覧

状態は、メールアドレス・パスワード・**メールアドレス登録用トークン**（`client_email_registration_tokens`）の有無から導出する。カラムを持たないため、次の**判定順序**を上から順に評価し、最初に一致した状態を採用する（同時に複数当てはまるケースがあるため順序が必要）。

**判定順序**

1. `clients.password` が非 NULL → **利用中**
2. `clients.email` が非 NULL（`password` は NULL） → **初回設定待ち**（有効なメールアドレス登録用 URL が同時に存在しても、こちらを優先）
3. `clients.email` が NULL かつ、対象クライアントの `client_email_registration_tokens` に `is_used = false` の行がある → **メールアドレス登録待ち**（`expires_at` は問わない。期限切れの未使用トークンだけを持つ場合もこの状態）
4. 上記いずれにも当てはまらない → **メールアドレスなし**

**期限切れの添え書き**は、状態が「初回設定待ち」または「メールアドレス登録待ち」のとき、**対応するメールアドレス登録用トークン（`client_email_registration_tokens`）の最新 1 件の `expires_at` が `now()` を過ぎているか**で判定する。ログイン用リンク（`client_login_link_tokens`）の `expires_at` は参照しない（発行し直し直後はログイン用リンクが未生成のため、判定基準にできない。設計方針上、ログイン用リンクは登録用トークンの期限を引き継ぐだけの存在）。

- 対象クライアントに対応するメールアドレス登録用トークンが 1 件も存在しない場合（直接データを操作した等の想定外ケース）は、**期限切れとして扱う**

**判定のクエリ例**（Eloquent）：

有効・期限切れの区別を明示するために、`client_email_registration_tokens` を **「有効（未使用かつ期限内）」** と **「未使用トークンの最新期限」** の 2 軸で先読みする。行ごとに個別クエリを発行しない（N+1 を避ける）。

```php
// 一覧・詳細で共通に使う想定。1 クエリで状態導出に必要な 2 値を持たせる
$clients = Client::query()
    ->addSelect([
        // 「有効な（未使用・期限内の）メールアドレス登録用トークンの有無」= 1 or 0
        'has_active_email_reg_token' => ClientEmailRegistrationToken::selectRaw('1')
            ->whereColumn('client_id', 'clients.id')
            ->where('is_used', false)
            ->where('expires_at', '>', now())
            ->limit(1),
        // 「最新の未使用トークンの期限」= 期限切れかどうかの判定に使う
        'latest_email_reg_expires_at' => ClientEmailRegistrationToken::select('expires_at')
            ->whereColumn('client_id', 'clients.id')
            ->where('is_used', false)
            ->orderByDesc('id')
            ->limit(1),
    ])
    ->get();

// ステータス導出（アクセサ or Enum ヘルパで表現）
foreach ($clients as $c) {
    if ($c->password !== null) {
        $status = 'in_use';                    // 利用中
    } elseif ($c->email !== null) {
        $status = 'awaiting_setup';            // 初回設定待ち
    } elseif ($c->latest_email_reg_expires_at !== null) {
        $status = 'awaiting_email';            // メールアドレス登録待ち
    } else {
        $status = 'no_email';                  // メールアドレスなし
    }

    // 期限切れの添え書き（有効なトークンが 1 件もない場合に付ける）
    $isExpired = in_array($status, ['awaiting_setup', 'awaiting_email'], true)
        && ! $c->has_active_email_reg_token;
}
```

**状態一覧**

| メールアドレス登録待ち（期限切れ） | `email` NULL、`is_used=false` のメールアドレス登録用トークンはあるが有効期限内のものはない | 登録待ち（期限切れ） | `bg-danger` | 「マイページ登録案内を発行」（**期限切れは未発行と同じ扱い**。押下でその場で新規発行する。取消は出さない — もう使えない案内を取り消す意味がないため） |
| メールアドレスなし | `email` NULL、`is_used=false` のメールアドレス登録用トークンが 1 件もない | なし | `bg-secondary` | 「マイページ登録案内を発行」 |

**備考**：
- **状態別ボタンは基本 1 つだけ**。ただし**「メールアドレス登録待ち（期限内）」のときだけ「マイページ登録案内を表示」と「マイページ登録案内を取消」の 2 つが並ぶ**（表示と取消は性質の違う操作 — 渡す／やめる — で、どちらも必要なため）。「クライアント一覧に戻る」「編集」「削除」は状態にかかわらず常に表示する
- **期限内に発行し直す機能は用意しない**：URL がまだ使えるので、もう一度渡せば足りるため（詳細は 6-3-6 の備考）
- **期限切れの URL は詳細画面に表示しない**：期限切れの URL はもう使えず、トレーナーが確認する意味がないため、未発行と同じ扱いにする
- 「メールアドレスを削除」ボタンは**利用中のときだけ**表示する。他の状態では clients.email や clients.password の一部が既に NULL のため、削除操作の効果が不明確になり、意図せぬデータ破損を招くおそれがある
- **期限判定の唯一の参照元は `client_email_registration_tokens.expires_at`**。ログイン用リンク（`client_login_link_tokens`）の `expires_at` は本判定では使わない（発行し直し直後はログイン用リンクが未生成であり、判定の基準にできないため）。ログイン用リンク側の `expires_at` は登録用トークンの `expires_at` を引き継ぐだけの派生値であり、単一の真の値は登録用トークン側にある

#### S-0307 メールアドレス登録用 URL 印刷画面

##### 概要

発行済みのマイページ登録案内（QR コード・URL・手順・有効期限を載せた紙面／画面）を、ブラウザの印刷機能で紙に出したり、面談中に画面や QR コードでそのままお客様に見せたりするための専用ページ。**入口は 1 つ**で、S-0305 詳細画面の「**マイページ登録案内を表示**」ボタン（状態が「メールアドレス登録待ち（期限内）」のときに表示）を押すと、**別タブで**開く（発行直後の自動遷移は行わない — 経緯は requirements.md 6-3-6 備考を参照）。**画面名は「メールアドレス登録用 URL 印刷画面」のまま維持する**（設計書上の画面名として。お客様に見せる見出しは「マイページ登録のご案内」）。

##### 備考

- **印刷専用のレイアウトを新規に用意する**（例：`layouts.print` として `layouts.app` とは別に置く。ナビゲーションバーもフッターも最初から出力しない）。既存レイアウトを CSS の `@media print` で隠す方式は取らない。理由は 2 点：
  - 隠す方式より確実（ロゴやサブナビの取りこぼしを避けられる）
  - 通常表示と印刷で見た目が変わらないため、トレーナーが画面で確認したものがそのまま紙に出る
- ページの余白・改ページ・用紙サイズ（A4 想定）など、**印刷でしか効かない指定**は必要に応じて `@media print` の `@page` ルール等で調整してよい。要素の表示・非表示を切り替える目的で `@media print` を使うことは原則しない（表示・非表示はレイアウト側で完結させる）。**例外**：「クライアント詳細に戻る」リンクは画面には出して紙には出さないというトレーナー専用の要件があり、代替手段がないため `@media print` で非表示にする（Bootstrap の `d-print-none` ユーティリティが該当）。この一点のみ例外として認め、他の目的での `@media print` による表示切替は引き続き行わない
- URL 文字列は QR が読み取れないときの手入力を想定し、ハイフンや `/` の直前で自然に折り返せるよう、等幅フォント＋ `word-break: break-all` を適用する
- **有効期限は日付のみ**を大きく表示する。時刻（`H:i`）はここには載せない（紙で読むとき「23:59 まで有効？ 24:00 まで？」の混乱を避けるため、日付だけの粒度に統一する）

##### 操作フロー

1. 録音開始前: 「開始」をクリックすると、録音中になる
2. 録音中:
   - 「停止」をクリックすると、録音停止処理 → 録音完了の確認ダイアログを表示
   - 「一時停止」／「再開」で録音の一時停止と再開が可能
3. 録音停止処理:
   - 音声記録を登録
4. 録音完了の確認ダイアログ:
   - 「OK」をクリックすると、トレーニング記録作成の確認ダイアログへ
5. トレーニング記録作成の確認ダイアログ:
   - 「はい」: トレーニング記録作成モーダル（S-0502-M01）を表示
   - 「いいえ」: 音声記録のみ保存され、ログアウト
6. トレーニング記録作成モーダル（S-0502-M01）:
   - 必要項目を入力
   - 「作成」: トレーニング記録作成中になる
   - 「キャンセル」: 音声記録のみ保存され、ログアウト
7. トレーニング記録作成:
   - 文字起こしを実行し、音声記録に設定
   - 要約を実行し、音声記録に設定
   - トレーニング記録を登録し、要約をトレーニング記録に設定
   - 処理完了後、ログアウト
8. ログアウト: 処理中表示を出してログアウト処理を実行

##### 備考

**セキュリティ設計**:
- クライアント名を表示しない（画面録画・覗き見による情報漏洩防止）
- 録音中・録音停止後の処理完了までは、他の画面への遷移を完全にブロック
- 録音中に画面を離脱しようとした場合は警告を表示
- 録音完了・トレーニング記録作成完了後は強制ログアウト

> **iPad Safari の制約（保留事項／bugs.md No.101）**: PC 版 Chrome／Edge では戻る操作の防止が動作しているが、iPad Safari では仕様上、JavaScript からの戻る操作の完全な無効化が技術的に困難。録音中に戻られた場合の録音データ消失は現状防げない。将来的には「定期的な中間データ送信」など、戻られても消えにくい仕組みでの対策を検討する。

**録音形式**:
ブラウザの MediaRecorder API を使用して録音する。デバイス（OS/ブラウザ）により記録される音声ファイル形式が異なる場合がある。

- ログインカード上部にロゴ画像（`public/images/client-portal-logo.png`）を表示する。正式ロゴ未定のため仮画像を使用し、確定後に同名ファイルで差し替える
- 本画面は**初回設定を終えたお客様が 2 回目以降にログインする画面**の位置づけ。初めてご利用のお客様はメールアドレス登録用 URL（S-1405）から始まる
- ログインカード下部にヘルプ文「初めてご利用の方は、担当トレーナーから受け取った URL からお進みください」を配置する
- **カード下の 2 つの案内（「パスワードを忘れた方」と「初めてご利用の方は……」）の並び順**：まず「パスワードを忘れた方」のリンク（お客様の直近の困りごとに応える。既にお客様であることが前提の導線）を先に置く。続いて空行を挟み「初めてご利用の方は……」のヘルプ文（初めて訪れた方向けの案内）を後に置く。理由は、本画面が「初回設定を終えたお客様が 2 回目以降に来る画面」の位置づけで、パスワードを忘れた方が最も多く必要とする導線であるため。並び順の詳細は `docs/client-portal-design-plan.md` §4-3 に従う
- **メールアドレス変更完了時**：メールアドレス確認リンクを開いた場合、クライアントの状態（ログイン中／未ログイン）にかかわらず、切替後は自動的にログアウトして本画面へ遷移する。動作を統一する（新しいアドレスでログインできることをその場で確かめられるようにするため。決定事項 #9）
- **パスワード再設定完了時**：パスワード再設定画面（S-1408）でパスワードを設定した直後に本画面へ遷移し、フラッシュメッセージを表示する。設定完了時点でお客様にログインさせない（新しいパスワードで実際にログインできることをその場で確かめてもらう。詳細は 6-15-12 の備考）

##### 備考

- **ログイン用リンクを開いただけでは使用済み（is_used=true）にはしない**。使用済みマークは「設定して進む」を押した時点（初回設定を送信した時点）のみ
- **二重開封時の挙動**：複数の端末やタブでリンクを開いた場合、GET は使用済みにしないため両方でフォームを表示できる。先に「設定して進む」を押した端末が成功しトークンが使用済みになり、後から送信した端末はエラー（使用済み）状態を表示する
- **有効期限の取り扱い**：ログイン用リンクの `expires_at` は、対応するメールアドレス登録用 URL の `expires_at` をそのまま引き継ぐ（お客様がメールアドレスを登録した時点から数え直さない）。したがって「メールアドレス登録用 URL の発行から 3 日」が初回設定完了までの全体の期限となる
- **画面構成は S-1406 / S-1411 と揃える**（`layouts.client-public` を extends する pre-auth 画面である点は据置、内部の構造だけを揃える）：
  - **見出し「初回設定」はカードの外（上）**に置く。S-1406「登録情報」、S-1411「登録情報の変更」と同じ位置。ページ内の情報階層を他画面と対応させる
  - **セクション見出し（旧「── パスワード ──」「── お名前 ──」「── ご連絡先 ──」）は置かない**。理由：横線付きの装飾（`.eyebrow` に `── ── 装飾`）は**お客様側の他のどの画面にも出てこない形**で、残すとここだけ浮く。お客様側の確認・表示画面は縦一列を標準としており（`client-portal-design-plan.md` §2-3）、入力フォームもその考え方に沿って項目を素直に並べる。項目数が多いので後から「区切りがあった方が読みやすい」と考えて復活させたくなるが、余白（`.mb-2` / `.mb-3`）で自然に区切られるため装飾は不要
  - **説明文（旧「〇〇のパスワードとご連絡先を設定します」）は置かない**。代わりに**カード先頭に「メールアドレス」の表示のみの行**を置く（S-1411 の「お名前」表示行と同じマークアップ）。理由：（1）S-1406 でもメールアドレスは表示項目の先頭にあるので位置が対応する、（2）初回設定はログイン ID を確認する場面でもあり、文の中に埋め込まれているより行として立っている方が目に入る、（3）説明文をやめることで「ご連絡先」という語がこの画面から消える
- **姓・名、せい・めいは横二列のまま維持**（`.row.g-2` + `.col-sm-6` の 2 列グリッド）。理由：**姓名は対で入力するもので横に並ぶのが自然**。スマートフォンでも項目 2 つなら収まる。**縦一列の標準（`client-portal-design-plan.md` §2-3）に対する意図的な例外**であり、後から縦に直さないこと
- **パスワード要件の補足文**（`.form-text` の「8 文字以上で…」）は入力欄直下に残す。位置・マークアップは S-1410 の同じ補足文と揃っている
- **表示のみの行は S-1411 の「お名前」と同じマークアップに倣う**：`<div class="mb-3">` の中に `<div class="text-muted small">ラベル</div>` と値の `<div>` を並べる形。同じ役割の要素が二画面で違う書き方になるのを避けるため
- **カード内に 2 本の区切り線を引く**（**入力欄のまとまりの境目に引く**、が定義）：
  1. パスワード（確認）の下（パスワード／氏名の境目）
  2. めいの下（氏名／連絡先の境目）
- **メールアドレスの表示行の下には線を引かない**（今回削除）。理由：ここは「まとまりの切り替わり」というより**「読む部分と書く部分の切り替わり」**であり、メールアドレスの行は他と見た目が違う（小さいラベルと枠のない値）ので線がなくても区切られて見える。線の役割が薄い
- **パスワードの下・氏名の下に線を引く理由**：入力欄と入力欄の境目で、**見た目が同じ要素（`.form-control`）が続くため、線がないと切れ目が分からない**
- **連絡先まとまりの下（最終まとまり）には線を引かない**。理由：**カードの枠が外周を担当しているため、カード内側の下端に線を引くと役割が重複する**（S-1406 で決めた考え方と同じ）
- **S-1406 の罫線との役割の違い**（**混同しないこと**）：
  - **S-1406 の罫線**：項目と項目の間を区切る（**一項目ごとに一本**）。確認画面は 1 行 = 1 項目で、項目単位が意味を持つ
  - **S-1403 の区切り線**：入力欄のまとまりとまとまりの間を区切る（**複数の入力欄をひとまとめにして境目に一本**）。入力フォームは項目数が多く、内容の性格でまとまりを作る方が読みやすい
  - 役割が違うので、**S-1403 に項目ごとの線を引いたり、S-1406 の線をまとまり単位にまとめたりしない**
- **経緯**（同じ検討を繰り返さないために残す）：
  1. 元は各まとまり見出し `── パスワード ──` などの装飾でまとまりを示していたが、装飾がお客様側の他画面にない形で浮くため、装飾を外して項目を素直に並べた
  2. その結果、まとまりの境目が分かりにくくなったので、いったん**「4 つのまとまりを等しく区切る」として 3 本の線**を引いた（メール／パスワード／氏名の 3 箇所の下）
  3. 実物を見ると、メールアドレス下の線は「まとまりの切り替わり」ではなく「読む部分と書く部分の切り替わり」で、行の見た目が違うので線がなくても区切られて見えた。線の役割が薄い
  4. そこで**定義を「入力欄のまとまりの境目に引く」に変更**し、メールアドレス（入力欄ではない）は対象外にして、**線を 2 本にした**
- **実装方法**：まとまり最後の**入力欄**要素に Bootstrap の `pb-3 border-bottom` を追加（`mb-3` は元々の下余白として維持）。S-1406 は各項目に `py-3 border-bottom` を付ける形だが、S-1403 は入力欄が既に上下方向の内部空間を持つため、下側の `pb-3` だけを追加する非対称形にした。SCSS 変更なし

- 発行済みの URL は初回設定が完了するまで有効。**「登録して進む」を押すたびに前のログイン用リンクを無効化して新しいリンクを発行する**（同じアドレスの再入力・別アドレスへの入力し直しの両方に対応）

- **重複アドレスが入力された場合**：バリデーションでエラーを返し、`clients.email` は更新しない。メールアドレス登録用 URL のトークンは有効なまま残り、別のアドレスで入力し直せる
- 完了状態で入力されたメールアドレスを表示するのは、打ち間違いにその場で気づけるようにするため（決定事項 #11）
- **完了状態のカード下部に「メールアドレス入力に戻る」ボタンを置く**：ボタン文言に「戻る」を含めて「入力画面へ戻る」動きが伝わる形にしている。案内文（手元 URL から入り直す方法）とボタン（画面上から入り直す手段）の 2 経路を用意することで、メールを見て気づいた人はボタンを、画面を閉じてしまった人は URL を使える
- 特定の 1 件だけを狙って無効化する UI は用意しない。トレーナー側からの無効化は「再発行」（未使用の登録用 URL とログイン用リンクをまとめて置き換え）、「マイページ登録案内の取消」（6-3-7）、または「メールアドレスの削除」（6-3-8）で行う

#### S-1406 クライアント登録情報画面

##### 概要

ログイン中のお客様が、自分の登録内容を**確認する**画面。氏名・住所・電話番号・メールアドレスなど、システムに登録されている自分の情報を一覧できる。あわせて、登録情報の変更（S-1411）、パスワードの変更（S-1410）、メールアドレスの変更（S-1409）への**入口**（ボタン）を置く。ダッシュボード（S-1402）のナビの「登録情報」から遷移する。

##### 画面を二階層にした理由

**旧設計では、「登録情報」をクリックするといきなり変更フォームが表示されていた**（一般的な会員登録サイトでは「確認 → 変更」の二階層になっていることが多い）。この作りだと**自分の登録内容を確認するだけの用途に応えられない**（変更画面には表示のみの項目やパスワードのマスクが混ざり、確認用には情報が読み取りにくい）。**確認画面と変更フォームを分ける**ことで、確認だけしたいときと変更したいときの両方に応える。

##### S-1406 という画面 ID を確認画面側に据えた理由

新設は「確認画面」と「変更フォーム」の二つ。**画面 ID S-1406 は確認画面側に残し、変更フォームには新番号 S-1411 を割り当てる**。理由は、**ヘッダーの「登録情報」というリンク名が指す先の画面 ID が S-1406 のまま**になり、画面名（登録情報）と画面 ID の対応関係がねじれないため。逆に、変更フォームを S-1406 に残して確認画面を新番号にすると、「登録情報」という画面名の指す先が新番号側に移り、後から設計書を読む人が「登録情報 = S-1406」の直感と食い違って混乱する。

##### 備考

- **表示レイアウトは縦一列**（ラベル上・値下、**項目と項目の間だけに罫線を引く**）。**お客様側の確認・表示画面の標準**（`docs/client-portal-design-plan.md` §2-3 参照）。理由：**お客様側の画面はスマートフォンでの閲覧を想定している**ため、横に並べると視線が横に飛んで読みにくく、縦一列で 1 項目ずつ読める形にする。カードの枠が外周を担当するので、カード内側の上端・下端にも罫線を引くと役割が重複するため、罫線は項目の区切りにだけ引く
- **`x-detail-cell` は使わず、専用のマークアップにする**。`x-detail-cell` はトレーナー側のクライアント詳細画面（S-0305）と共用で、3 列グリッドを前提にしている。トレーナー側は情報量が多く一覧性が要るので 3 列が適切、お客様側は項目が少なく確認用途なので縦一列が適切。用途が違うため実装を分ける
- **並び順の先頭にメールアドレスを置いた理由**：メールアドレスは**ログイン ID を兼ねている**ため、確認画面で最初に目に入る位置に置く。以降はお名前・かな・住所・電話番号 …… と、識別情報から連絡先へと自然な流れで並べる
- **ラベルは「メールアドレス」のままとし、「ID（メールアドレス）」等にはしない**。ログイン画面（S-1401）の入力欄のラベルが「メールアドレス」であり、変更画面（S-1409）の画面名も「メールアドレスの変更」なので、**呼び名を一つに保つ**ことでお客様が同じものだと迷わずに認識できるようにする
- **未入力の項目はラベルを残し、値を空にする**（行ごと消さない）。確認画面なので**「登録されていない」ことが分かる必要がある**。行が消えると、未登録なのか項目自体がないのかを区別できないため
- **表示項目にパスワードは含めない**。パスワードは表示しても情報量がない（実値はマスクされ、「設定済み」等を出しても新しい情報にならない）ため、確認画面では省く
- **住所の組み立て**：郵便番号・都道府県・市区町村・町名番地は 1 行にまとめる。建物名・部屋番号は次行に分ける。要素が未入力ならその要素だけスキップする（区切りの空白や記号は残さない）
- **入口ボタンの見た目**：3 つとも `.btn-primary`（明るいオレンジ `#EC6812` の塗り、白文字）で揃える。同格の入口だから優劣を付けない
- **入口ボタンの並び順は「メールアドレスを変更 → パスワードを変更 → 登録情報を変更」**（上の表示項目の並びと同順）。理由：**表示項目の並び（メールアドレスを先頭）とボタンの並びを対応させて画面全体の筋を通すため**。「登録情報を変更」が最下段になるが、ボタンは 3 つだけで全部が一目に入るため上下の位置による使いやすさの差はほとんどなく、表示項目との対応を優先した
- **ボタン文言と画面名の使い分け**：ボタン文言は動作を表す「〜を変更」、遷移先の画面名（見出し）は名詞形の「〜の変更」。日本語として「〜を変更する（動作）」と「〜の変更（対象）」が別語形になるため、それぞれの役割に合わせて使い分ける
- **画面 ID の据え方**：本画面（S-1406）は確認画面、変更フォームは新番号 S-1411。上の「S-1406 という画面 ID を確認画面側に据えた理由」を参照
- **メールアドレス確認リンクはログイン用リンクとは性質が異なる**：メールアドレスを切り替えるだけの役割で、リンクを開いた側でログイン状態にはならない。ログイン状態を問わず同じ処理（切替 → ログアウト → ログイン画面へ）を行う（詳細は S-1409 の備考）
- **画面下部に案内文（「利用をやめたい場合は担当トレーナーにご連絡ください」等）は置かない**。理由：
  - システムの利用をやめることと、トレーニングの契約を終えることは別の話
  - アカウントをいつ削除するか（契約終了時、一定期間未利用時など）は**訓練所とお客様の契約で決まる事柄**であり、システムの画面が独自に案内する範囲を越える
  - **アカウントの存続と終了はシステムが規定する事柄ではなく、訓練所とお客様の契約で決まる**、という切り分けに従う
- **氏名・かなの変更の導線を画面上に置かない**（**保留**）。お客様側では氏名・かなが変更不可のため、変更したい場合はトレーナーに連絡してもらう必要がある。画面上に「氏名の変更はトレーナーへ」といった案内を置くかどうかは、**実際に運用してみてから決める**。**現時点では意図的に置いていない**（不備ではなく保留である。詳細は `requirements.md` 6-15-9 の備考参照）

#### S-1409 クライアントメールアドレス変更画面

##### 備考

- **メールアドレスの変更は「申し込み → 確認リンク → 切替」の 2 段階**。本画面の送信では即座に切り替わらない。切替が完了するのは、新しいアドレスに届いたメールの「メールアドレス確認リンク」を開いた時点。切替が完了するとログアウトして S-1401 クライアントログイン画面へ遷移する（決定事項 #9）
- **メールアドレス確認リンクはログイン用リンクとは性質が異なる**：メールアドレスを切り替えるだけの役割で、リンクを開いた側でログイン状態にはならない。ログイン状態を問わず同じ処理（切替 → ログアウト → ログイン画面へ）を行う
- **同時に有効な確認リンクは 1 本のみ**（決定事項 #6）。この画面で申し込みを送るたび、それまで未使用の既存トークンは物理削除する（新しい確認リンクだけが有効）
- 送信完了後は**同画面（S-1409）自身に戻り**、フォーム上部に「新しいメールアドレス宛に確認メールを送信しました…」を表示する（共通レイアウトの `session('success')` 受け皿を使う）
- バリデーションエラーも同画面（S-1409）にとどまり、フォーム上部に表示する
- **現在のメールアドレスの表示（現在値の再掲）は置かない**。理由：
  - **直前の S-1406（登録情報）で見たばかりの情報の再掲**になる。S-1406 ではメールアドレスがログイン ID を兼ねるため表示項目の先頭に置いており、お客様はその値を見てからこの画面へ来る
  - **フォームの入力項目が「新しいメールアドレス」「現在のパスワード」の 2 つだけ**なので、上に表示のみの行があると、どれが入力欄なのかが一瞬分かりにくくなる
- **S-1411（登録情報の変更）に氏名・かなが表示のみで残っているのは意図した違い**。性格が異なる：
  - S-1409 の「現在のメールアドレス」は**変更できる項目の現在値**の再掲。同じ画面に「新しいメールアドレス」を入れる欄があるので、現在値を出さなくても用は足りる
  - S-1411 の氏名・かなは**変更できない項目**を示している。表示を消すと「この画面では氏名は変えられない」ことが伝わらなくなる
  - よって「変更フォームで現在値を出すか出さないか」を一律に揃えるべきではない。項目の性格ごとに判断する
- **送信ボタンの文言は「確認メールを送る」のまま**（S-1410 / S-1411 が「変更する」に統一されたが、本画面は揃えない）。理由：**本画面の送信は「変更を完了する」操作ではなく「確認メールを送る」操作**で動作の性格が違う。実際の切替はメールのリンクを開いた時点で起きるため、押した瞬間の動作を正しく表す文言として「確認メールを送る」を維持する

- **パスワードの変更はログアウトさせない**（決定事項 #12）。画面内で完結し、メールのリンクを経由しないため

- 送信完了後は**同画面（S-1410）自身に戻り**、フォーム上部に「パスワードを変更しました」を表示する（共通レイアウトの `session('success')` 受け皿を使う）

- **氏名は表示のみ**で、この画面からも変更できない（初回設定の項目であり、変更が必要な場合はトレーナーに依頼）
- 送信完了後は**同画面（S-1411）自身に戻り**、フォーム上部に「登録情報を変更しました」を表示する（共通レイアウトの `session('success')` 受け皿を使う）
- バリデーションエラーも同画面（S-1411）にとどまり、フォーム上部に表示する

  - **「保存」を使わない**：お客様側は「変更」で語彙を統一しており、「保存」を持ち込むと言葉が一つ増える
  - **「登録情報を変更」にはしない**：S-1406 の**入口ボタンが「登録情報を変更」**なので、同じ文言にすると押す場所も意味も違うのにどちらを指すか分からなくなる。目的語を落として「変更する」にすれば、画面名が「登録情報の変更」なので**何を変更するかは文脈で伝わり**、入口ボタンと区別できる

  - **ボタンは画面名の直下にある**ため何を変更するかは文脈で伝わり、目的語を付けると S-1406 の入口ボタンと同じ文言になってしまう
  - **完了メッセージは操作の後に目に入る**ため、何が変わったのかを明示した方がお客様が安心できる
  - 一見ちぐはぐだが、置き場所と役割の違いに応じた自然な使い分けで、揃えるべきではない

#### メールアドレス確認リンク（S-1409 からの派生。専用画面は持たない）

メールアドレスの変更で送信されるメールアドレス確認リンクは、**独立した画面を持たない**（切替後に S-1401 へ遷移するのみのため）。ただし、リンクが無効・期限切れ・使用済みの場合は、既存の無効トークン画面（`client/setup/invalid-token.blade.php` と同じ「pre-auth の説明カード」）を使ってエラーを表示する。

| 状態 | 条件 | 表示 |
|------|------|------|
| 有効 | トークンが存在し、未使用・有効期限内 | メールアドレスを切り替え、ログアウトして S-1401 へ遷移。S-1401 に「メールアドレスを変更しました。新しいメールアドレスでログインしてください」を表示 |
| エラー（無効） | トークンが存在しない | 無効トークン画面「このURLは無効です」 |
| エラー（期限切れ） | 有効期限を超過 | 無効トークン画面「このURLは期限切れです」 |
| エラー（使用済み） | すでに切替済み | 無効トークン画面「このURLは既に使用されています」 |

有効な場合の**重複再確認**（申し込みから確認までの間に他クライアントが同じアドレスを登録した場合の扱い）：切替の直前に重複を再チェックし、重複していれば切替を止めて無効トークン画面「このメールアドレスは登録できません。担当トレーナーにご連絡ください」を表示する（トークンは使用済みにしない）。

- **設定完了時にログインさせない**（決定事項 #6 / 6-15-12 の備考）：新しいパスワードで実際にログインできることをその場で確かめてもらう
- **完了を通知するメールは送らない**（決定事項 #7 / 6-15-12 の備考）：再設定リンク自体が登録アドレスに届いているため、本人はすでにメールを受け取っている
- 「パスワード再設定リンク」はログイン用リンク（S-1403）・メールアドレス確認リンク（S-1406）とは性質が異なる：**新しいパスワードを設定するためのリンク**であり、ログインさせる働きは持たない・メールアドレスも変えない。無効トークンビューは既存のもの（`client/setup/invalid-token.blade.php` の「pre-auth の説明カード」）を流用する
- **ログイン中に本画面へアクセスした場合の扱い**：ログアウトさせず、ログイン状態は維持する。詳細は要件定義書 6-15-12 の備考「ログイン中に再設定リンクを開いた場合の扱い」を参照

## 4. 画面実装ガイドライン

### 4-1. カードの使い分け

カードは、画面項目を視覚的に「グループ」として括る場合（検索条件・フィルタ、セクションなど）に使う。「グループ」として意味を持たない場合は使わない。

---

### 4-2. ボタンの配置

画面右上（タイトル右側）に配置する。配置の結果、縦にスクロールが必要になる場合は、画面右上と右下の両方にボタンを配置する。

---

### 4-3. キャンセルボタンの有無

入力フォーム画面でキャンセルボタンを置くかどうかは、**明確な戻り先があるかどうか**で判断する。

| 画面の性質 | 例 | キャンセルボタン |
|---|---|---|
| **一覧画面から遷移し、明確な戻り先がある** | 登録、編集 | 置く |
| **システムの設定を変更する画面で、明確な戻り先がない** | 環境設定、パスワード変更 | 置かない |

---

### 4-4. ボタンの色

ボタンの色は、その操作が「**何をするものか**」によって決める。色そのものではなく、操作の意味で選ぶ。

| 操作の意味 | 例 | クラス（色） |
|---|---|---|
| **データ保存** | 登録、更新 | success（緑） |
| **遷移** | 詳細、次へ、検索 | primary（青） |
| **削除** | 削除 | danger（赤） |
| **副次操作** | キャンセル、戻る、閉じる、クリア | secondary（灰） |

#### 視覚的階層

- **塗りつぶし**: 主要なアクション、業務上頻出する操作
- **白抜き（outline）**: 補助的な操作、頻出しない操作

---

### 4-5. 入力フォームのレイアウト

登録・編集画面の入力フォームは、ラベルを左・入力欄を右に横並びにする水平レイアウトを標準とする。縦積みに比べて縦スクロールが減り、視線とマウスの移動距離が短くなる。

**ラベル**

ラベルは左に置き、幅140px固定・右寄せとする。140pxに収まらない長いラベルは個別に縮小する。

**行の構成**

各行は独立した row で囲み、行間は mb-2 とする（最終行は付けない）。

**列幅（col）**

項目の内容量に応じて col を決める。

**プルダウンの初期選択肢**

未選択状態を表す先頭の option は表示テキストを空にする。

**autocomplete**

ブラウザの誤オートフィルを防ぐため、全 input / select に autocomplete="off" を付ける。
